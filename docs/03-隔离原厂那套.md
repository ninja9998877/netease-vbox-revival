# 03 · 隔离原厂那套

> ★ **这是全文最重要的一章。**
>
> 如果你只想看一篇，就看这篇。我在这上面栽的跟头比在其它所有环节加起来都多。

## 先记住一句话

> ### 原厂那套东西，**不杀、不替换**。我寄生在它旁边。

很多人（包括一开始的我）第一反应是："厂商的服务都死了，那把它的进程杀掉、
把它占的资源抢过来不就行了？"

**不行。而且这是最危险的想法。**

因为原厂固件里其实有**两套东西**，它们看起来是一伙的，实际命运完全不同：

| | 是什么 | 状态 |
|---|---|---|
| **网易云端** | 语音识别、对话、音乐、语音合成、长连接、OTA | ☠️ **已死**，必须绕过去 |
| **设备本地服务** | 唤醒引擎、麦克风采集、喇叭播放器、D-Bus 控制网、LED 驱动 | ✅ **还活着**，是地基 |

**设备本地的任何一个服务，关掉都会让设备直接变砖。**

所以正确的姿势是：**把云端那一层绕过去，把本地这一层借过来用。**
下面四个手法，就是我实际做的事。

---

## 手法一 · 隔离：让它照常跑，我在旁边接一份

### 麦克风：拷一份，不是抢过来

最开始的直觉是"我直接打开声卡录音不就行了"。

**试了就知道不行**——你一独占打开声卡，原厂的唤醒引擎立刻瞎了。
它再也听不见唤醒词，整台设备就彻底哑了。这是**同归于尽**的做法。

我最后用的办法，是**在动态库层面把它的读取函数换掉**：

- 原厂唤醒引擎从麦克风读音频，走的是一个标准函数 `snd_pcm_readi`
- 我用 `LD_PRELOAD` 把自己的库注入进它的进程
- 我的库里实现了同名的 `snd_pcm_readi`：**先调用原来的函数拿到真实数据，
  然后拷一份发走，原样返回给调用者**
- 对原厂引擎来说，**什么都没发生**——它拿到的是同一份数据、同一个返回值

**关键点：只截"读取"，不截"打开"。** 声卡的打开、参数配置、关闭全部放行，
一点状态都不改。这样两边永远不打架。

> ★ **坑：`LD_PRELOAD` 有时序窗口。**
> 注入得晚了，符号已经被解析过了，你的库**根本不会生效**——而且**不报错**。
> 表现是"代码明明写对了，就是没反应"，能让你查一整天。
> 判断方法：让它往一个文件里写一行心跳，看文件在不在。**别靠猜。**
>
> ★ 另一个坑：库文件必须放在**根文件系统**里（`/lib` 之类）。
> 放在外挂存储上会被**静默忽略**——同样不报错。

### 出声：借它的播放器，绝不抢声卡

出声这件事只有一条规矩：

> ### 设备上唯一合法的"嗓子"是原厂的那个播放器。

它内部有一个多进程的服务网（走 D-Bus 通信），其中**播放器服务**是负责出声的那个。
你只要**用 D-Bus 命令它播一个 URL**，它就会自己去下载、解码、播放。

- ✅ 正确：发一条 D-Bus 命令，带上网址，让它播
- ❌ 错误：自己打开声卡往里写 PCM 数据

自己抢声卡的后果是：你的音频和原厂的播放**互相踩**，
轻则断续重则两边都哑，而且你会以为是自己的代码有问题——其实是从一开始就错了路。

★ **顺便说：麦克风的"打开"和"读取"我分了家，出声这条我是整个绕开——从始至终没碰过声卡的播放侧。**

### 进程：一个都不杀

原厂的进程我**一个都没杀**。我只在它**加载的时候**注入我的库。

杀进程的诱惑很大（"它都在空转了，杀了省资源"），但那些进程同时也在提供
唤醒、播放、LED 这些能力。**你分不清哪些是垃圾、哪些是地基。**

## 手法二 · 指向黑洞：让它快速失败，而不是卡住等超时

原厂会不断尝试连回网易的服务器。既然那些服务器已经不存在了，
**最糟的情况不是"连不上"，而是"连不上还得等超时"**——那会拖慢一切。

做法很简单：**在 DNS 上把网易的域名解析到一个黑洞地址**，让它立刻失败。

**这个手法有个特别坑人的副作用，我在这上面误判过一整轮：**

> ★★ **黑洞只封 HTTP/HTTPS，ICMP 是通的。**
>
> 也就是说：你 `ping` 那些域名，**全部 0% 丢包，一片健康**。
> 你会得出结论"网络没问题啊"，然后去别的地方找原因——**方向彻底错了**。
>
> **判据修正：查连通性要查 TCP 端口，不要用 ping。**
> 黑洞环境下，ping 通 ≠ 服务可达。

### 顺带要防的一件事：原厂的 OTA

原厂有个进程会做**网络自检**：只要 ping 通了，它就认为"有网了"，然后去查新版本、试图升级。

- 这个自检是**边沿触发**的（ping 成功那一下触发），不是持续轮询
- 它的升级服务器有**证书校验**（后面"屏蔽"一节会说为什么这反而是好事）

所以我处理黑洞时，要把 OTA 相关的一并考虑进去——**别让它以为有网**。

---

## 手法三 · 屏蔽：堵掉它的徒劳重试

黑洞解决了"连不上"，但没解决"连不上还拼命连"。

### 堵长连接重试

原厂有一个云服务的 SDK，会维持一条长连接。服务端没了之后，它**每 50 秒**
徒劳重连一次，日志刷屏，**CPU 空转 26~48%**。

我的做法和截麦克风是同一招：**注入一个库，把它的登录/重登函数换成空函数**。
函数被调用时什么也不做、直接返回，SDK 就以为"登录过了"，不再重试。

> 注意：只是**让它别重试**，没有改动它的任何其它逻辑。

### 防 OTA：它的"证书墙"反而帮了我

我一度想过"伪造一个升级服务器，让它升级到我自己做的固件"。

**这条路是死的**，而且死得很干脆：

> 它的升级流程里，**证书校验排在签名校验之前**。
> 你过不了证书这一关，后面根本轮不到签名。

所以升级链是**攻不进去的**。但换个角度——**它同时也升级不到我**。
我要做的只是确保它连不上，剩下的它自己就完事了。

### 防"自我修复"：这是最容易被忽略的一环

★ **原厂的开机脚本会把某些关键开关改回"它认为对"的值——而那些值是错的**
（具体是哪两个开关，见下面"两个真凶"）。

这意味着：**你手动改好了，重启一次就打回原形。**
很多人会在这里怀疑人生："我明明改了啊？"

**正确的做法不是定时改回来，而是从源头改**——直接把原厂那个脚本里写死的值改掉。
（当然，定时兜底也留着，双保险。）

## 手法四 · 静音略过，然后给自己的线路让路

这一节是两个动作：**先把原厂的声音按下去，再把我的声音送出去。**

### 静音略过

原厂设备自己会发一些声音（提示音、错误提示）。我要让它闭嘴的时候：

- **用 mount 覆盖的方式**把它的音效文件顶掉（幂等，可重复执行）
- ★ **夜里**用**设备自己音频芯片的输出级开关**当硬闸门——这不是软件静音，
  是**输出级真的断开**。软件静音有可能被别的程序改回来，输出级断就是断。

### 让路：出口只走一条

前面说过，唯一的嗓子是原厂播放器。所以**我的音频全部走它**：

```
我的电脑合成好语音 → 起一个本地 HTTP 服务放这个 mp3
                  → D-Bus 命令原厂播放器："去播这个 URL"
                  → 设备自己来下载、解码、播放
```

★ **为什么不让设备直接播本地文件？** 因为播放器服务收的是 URL。
起个 HTTP 服务是最省事的做法，而且**能顺便控制码率、支持断点续传**。

### 坑：原厂会"占住"设备几秒钟

这是最阴的一个坑：

- 你喊唤醒词 → 原厂唤醒引擎要**占用设备若干秒**（播提示音、做处理）
- 这期间你推给播放器的音频，会被**判定优先级不够而压掉**
- 表现是："我明明发出去了，播放器也回我 OK 了，**但就是没声音**"

**我最初的修法是错的**：压掉了就重发，重发 2 次（约 1.5 秒）就放弃。
结果还是经常没声——因为**占用时间比 1.5 秒长**。

> ★ **正确修法：按时间补，不是按次数补。**
> 给一个时间预算（比如 8 秒），在这个窗口内持续补发；
> 同时判断"播放位置是不是已经在走了"——**在走就别补了**，否则会把话说两遍。

## ★ 开机必哑的两个真凶

这两个是我排查最久的问题，**而且答案都不在应用层**。
如果你照着做发现"改是改了、就是没声音"，八成是它们。

### 真凶一：一个声道选择开关

设备音频通路里有个左右声道选择开关，**出厂脚本把它写死了**。
而这台机器是**单声道喇叭，只吃左声道**——于是音频走进了一条**死路**。

- 现象：整机全哑，但所有软件层看起来都正常
- 这是**出厂固件自己的 bug**（左右不对称），跟我的改造无关
- ★ 关键：**源头那个脚本每次开机都会把它写回去** ⇒ 必须从源头改 + 定时兜底

### 真凶二：DAC 音量是 0

音频芯片有个**真正的硬件音量控件**，它的值是 **0**（约等于 -119dB，等于没有声音）。

- ★★ **这里有个大坑**：系统里还有好几个"看起来像音量"的控件
  （headphone volume、lineout volume、digital volume），**调它们全都没用**——
  **它们全是纸闸门**，真正管用的是那个 DAC 音量。
- 我在这上面浪费了很久，因为那几个纸闸门**改起来是有反馈的**（命令成功、值也变了），
  只是**对声音没有任何影响**。

> **怎么定位**：不要猜，**逐档实测**。
> 写个小脚本，把每个可疑的音量控件从 0 拉到某个值，看声音有没有变化。
> 一次只动一个。这是唯一可靠的办法。

## 一张表总结

| 原厂资源 | ❌ 会打架的做法 | ✅ 我的做法 | 一句话理由 |
|---|---|---|---|
| 麦克风 | 独占打开声卡录音 | 钩住它的读取函数，拷一份 | 独占 = 把它弄瞎 = 同归于尽 |
| 出声 | 自己往声卡写数据 | D-Bus 命令它的播放器播 URL | 抢声卡 = 两边都哑 |
| 进程 | 杀掉省资源 | 一个不杀，只在加载时注入 | 你分不清垃圾和地基 |
| 联网 | 直接断网 | DNS 指向黑洞，让它快速失败 | 卡在超时比连不上更糟 |
| 长连接 | 不管 | 空掉它的登录函数 | 每 50 秒白转，CPU 26~48% |
| 开机脚本 | 手动改，重启就没了 | 从源头改 + 定时兜底 | 它会自己改回去 |
| 提示音 | 调软件静音 | mount 顶掉 / 输出级断开 | 软件静音会被改回来 |
