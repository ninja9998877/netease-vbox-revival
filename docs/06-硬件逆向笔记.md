# 06 · 硬件逆向笔记

> 这一章是"零件库"。前面几章讲思路，这一章讲**具体长什么样**——
> 服务名、命令码、串口、控件。都是我一个个试出来的。

★ **先读 [07-危险操作清单](07-危险操作清单.md)**。这章里有几个接口，写错一个字节的后果
不是"没反应"，而是**把机器弄哑或弄砖**。

## 一、设备内部是一张 D-Bus 服务网

这是整台设备最重要的一张图。**原厂固件不是一个大程序，而是一堆互相通话的小服务**，
它们挂在同一条 D-Bus 会话总线上。

我逆向出来的关键角色：

| 服务 | 对象路径 | 干什么 |
|---|---|---|
| `netease.ihw.player` | `/netease/ihw/player` | **嗓子**。播放/停止，收 URL |
| `netease.ihw.controller` | `/netease/ihw/controller` | **总控**。管播放器、LED、状态机 |
| `netease.ihw.bt` | — | 蓝牙（A2DP Sink） |

它们共用一个接口：**`netease.ihw.SmartAudio.API`**。

### 调用签名（从总线原始报文反推出来的）

```
SmartAudio.API(uint32 flag, uint32 playerId, uint32 cmd,
               uint32 jsonLen, string json)
```

★ **五个参数一个都不能少、类型一个都不能错。** 少一个参数不会报错，
只会**静默地什么都不发生**。

### 三个特别容易错的参数

**① `jsonLen` 是 JSON 的【字节数】，不是字符数。**

★ 如果你的 JSON 里有中文，用 shell 的长度展开（`${#JSON}`）算出来的是**字符数**，
和字节数对不上 ⇒ 服务端解析失败。

> **正确做法**：`printf '%s' "$JSON" | wc -c`。
> 这个坑我在脚本注释里专门写了一条，因为**它只在有中文时发作**，
> 平时测都好好的，一上线就出问题。

**② 有个 `msgDests` 位图参数 = `1 << 模块号`。**

播放器模块号是 4 ⇒ 这个值要填 **16**。填错 = 命令发给了别人。

**③ `playerId` 必须等于总控当前认的那个播放器号。**

★ 如果对不上，总控会在日志里记一条
`Player(N) not the curPlayer(1) ... but in playing`，
**然后把你刚播的东西掐掉**。

> 表现是"明明播起来了，两秒后又没了"。
> **换设备/换固件时这条要重新确认**——它是个运行时的值，不是常量。

### 会话总线的地址是随机的（这个坑很经典）

设备上那条会话总线，socket 路径是 **`/tmp/dbus-XXXXXXXXXX`**——
**后缀每次开机都不一样**，由开机时拉起的总线守护进程生成。

所以：

- ❌ 不能写死路径
- ❌ 也不能只判断"这个文件存在"
- ✅ **必须判断"它是个 socket"**（`test -S`）

★ 还有一个更隐蔽的：**我们自己的服务环境里根本没有总线地址这个变量**
（实测进程环境里只有两个变量）。而 `dbus-send` 如果不知道去哪条总线，
命令会在**写进 socket 之前就被丢掉**——**一句报错都没有**，
表现就是"发出去了、喇叭没响"。

## 二、`dbus-send` 的两个反直觉参数

这一节值得单独列出来，因为**两个参数的直觉都是错的**。

### ① 必须有 `--print-reply`（哪怕你根本不要回执）

直觉："反正是单向命令，不要回执更快。"

**错。** 去掉它，`dbus-send` 会**不等消息 flush 就断开连接**，
消息烂在发送队列里，播放器一个字都收不到——
而 `dbus-send` 自己返回 0，**一声不响**。

实测（用播放器日志里的命令 ID 当判据）：

| 参数 | 结果 |
|---|---|
| 不带 `--print-reply` | ✗ **没送到** |
| `--print-reply --reply-timeout=2500` | ✓ 送到，但干等 2.546 秒 |
| `--print-reply --reply-timeout=200` | ✓ 送到，**0.239 秒** |
| `--print-reply --reply-timeout=50` | ✓ 送到，0.087 秒 |

### ② 超时必须**很小**

因为播放器是**只收不回**的——它收到命令就干活，**从不发 reply**。

于是 `dbus-send` 会一直干等到超时，然后吐一句 `NoReply` 错误。

★ **默认 2500ms 就是"每次说话凭空多等 2.5 秒"**。
而"停"这个命令是要在**打断**那一刻用的——那 2.5 秒就是**喇叭还响着的 2.5 秒**。

> **我最后用 200ms**：留了 4 倍余量（实测 50ms 也够，但总线忙起来时
> 发送+flush 本身要花时间，别抠）。
>
> ★ 而且注意：**这 200ms 只是 `dbus-send` 自己退出前的等待**，
> 命令早就送到了（flush 是微秒级的）。所以对"打断"来说，**真实延迟是 0，不是 200ms**。

### ③ 判成败**不要看这条命令的输出**

命令是单向的，`dbus-send` 本来就不回话。

> **真正的判据在接收端**：
> - 设备**有没有来取那个音频文件**（看你的 HTTP 服务访问日志）
> - 设备**播放器的日志里有没有那条命令 ID**
>
> **"它来取了"就是"成功"**——这是我整套系统里最可靠的一个判据。

## 三、命令码

设备内部用**数字命令码**通信。我摸出来的（十六进制）：

| 码 | 含义 |
|---|---|
| `0x601` | 播放（带 URL） |
| `0x602` | 停 / 掐断当前播放 |
| `0x603` | 停止 |
| `0x700` / `0x701` | 原厂自己的提示音 停 / 播 |

★ 有个概念要分清：**`0x601` 这类叫"命令码"，另有一层叫"总线命令"**
（`buscmd`），是发给**总控**的、管**状态与灯效**的那一层。
两层不要混，混了就是"发出去了没反应"。

## 四、串口：一根线三个用途

板子上有三个串口，**用途完全不同**：

| 串口 | 用途 |
|---|---|
| `ttyS0` | **根 shell**（115200）—— ★ 这等于一个后门 |
| `ttyS1` | 蓝牙服务在用 |
| `ttyS2` | **主控 → MCU 的 AT 命令通道** |

### ★★ 关于 `ttyS2`：绝不要盲写

那颗 MCU **同时管着**：

- 9×9 的 LED 点阵
- **音量旋钮的 ADC 采样**
- **触摸按键**

> **也就是说：你往这条串口上随便写字节，可能顺带改掉音量，或者触发触摸键事件。**
>
> **必须**：一次只发一个已知的命令码、发之前先想清楚、最好有人在旁边看着设备。

这也是为什么我在[危险清单](07-危险操作清单.md)里把它列为高风险项。

## 五、灯

### 灯环

- **按角度寻址（0–360°）**
- 状态灯（比如"倾听中"）由 buscmd 驱动，**有明确的命令码**
- ★ 你**观察**灯效就能反推设备当前在什么状态——**这是最方便的调试窗口**

### 9×9 点阵

- **单色**，走 `ttyS2` 的 AT 命令驱动
- 能做表情、能显示简单图案

★ **重要**：灯和声音是**两条独立的路**。
"灯亮了但没声音"和"有声音但灯不亮"是**完全不同的故障**，
先把这两条分开，能省很多时间。

## 六、音量：一个真杠杆和一堆纸闸门

这是我最想写给后来人的一节。

音频芯片（ADI ADAU1761，注册为 `card 0`）上有一堆看着像音量的控件。
**绝大多数是纸闸门——调它们命令会成功、值也会变，但对声音没有任何影响。**

### 真正的杠杆只有一个

| 控件 | 说明 |
|---|---|
| **`DAC volume`**（numid 19） | ★ **真杠杆**。所有路共同的增益底 |

参数（实测读出来的）：

```
min=0   max=255   step=0.75dB   dBscale-min=-119.25dB
⇒ 159 ≈ 0dB（满刻度）
```

> **它掉到 0 = -119.25dB = 全哑。**
> 而且**每一个"看起来该有声音"的环节都是对的**——状态机好、命令推得出去、
> 设备也真来取流了、功放静音也乖乖解开了，**就是一点声没有**。

**怎么定位**：★ **不要猜，逐档实测**。
写个小脚本，把每个可疑控件从某个值拉到另一个值，**一次只动一个**，看声音有没有变化。
这是唯一可靠的办法。

### 纸闸门们（别去动它们）

| 控件 | 真相 |
|---|---|
| `headphone volume` | 名字最像音量，**但不是真杠杆** |
| `digital volume`（numid 21） | ★ 曾经被我误判成真凶。**值是 0 也正常** |
| `DAC mixer gain`（numid 20） | ★ 同上，假线索 |

### 还有一个"路走错了"的真凶

除了增益为 0，还有一种全哑：**左声道被接到了一个空的模拟混音器上**。

设备音频通路里有个左右声道选择开关，它有两个位置：

- ✅ 正确位置：**DAC 直连耳机输出**
- ❌ 错误位置：**接进模拟混音器**——而那条路上的输入**全是关的**

设备是**单声道喇叭、只认左路**，所以走到错误位置 = **整机全哑**。

> ★ 而这**是出厂脚本自己写死的**（左右不对称的 bug）——
> 跟我改不改没关系，它在出厂状态下就会这样。
> 详见 [03 章](03-隔离原厂那套.md) 的"两个真凶"。

### ★★ 读 ALSA 控件的解析坑（这个坑很阴）

`amixer cget` 的输出长这样：

```
numid=19,iface=MIXER,name='DAC volume'
  ; type=INTEGER,access=rw------,values=2,min=0,max=255,step=1
  : values=150,150
  | dBscale-min=-119.25dB,step=0.75dB,mute=0
```

★★ **绝不能用 `tail -1` 取值**——最后一行是 **dBscale**，不是值。

用 `tail -1` 的后果：**永远读到 `-119.25dB`，永远判成"错的"，
于是每轮无脑写一次**。而且你会以为设备"一直在被人改回去"。

> **正确做法**：匹配 `  : values=` 那一行。
>
> ★ 同样的坑在另一个控件上也踩过一次——**两个脚本、同一条铁律**。

### 日志要报"结果"不是"意图"

写完控件之后**要读回复核**，读回对了才说"已扳回"。

★ 因为：**"说成功了"必须真的是成功了**，否则这个守护自己就成了假消息来源。
我们这个项目在这上面栽过跟头。

## 七、麦克风硬件

| 项 | 值 |
|---|---|
| 采集前端 | **CX20810**（★ 注意：**它不是回声消除器**） |
| 挂在哪 | 音频 DSP（ADAU1761）上 |
| 声卡 | **card 1**（`/dev/snd/pcmC1D0c`） |
| 被谁占 | 原厂语音进程**独占** |
| 真机格式 | **96000 Hz × 2 声道 × S24_LE** |

★ **回声消除是另一块固件**，而且它有个关键特性：
**只吃设备自己的语音合成输出，不吃外部推流。**

> 这一条我一开始猜反了——我以为"外部推流也会被 AEC 吃掉"，
> 于是绕了很多弯路。**实测才知道它只认设备自己那条链。**

## 八、零碎但值钱的坑

### ① 主机名里带中文，会让整行台账被静默丢弃

我维护一份设备的台账文件（IP ↔ 主机名 ↔ MAC）。
有一次加了一台**主机名带中文**的设备，**整行**被守护进程**静默丢弃**——
不报错、不警告，只是那行不生效。

> **教训**：往配置文件里加非 ASCII 之前，先确认那个解析器认不认。

### ② 改配置别用 `kill $(pidof xxx)`

★ **有的守护进程被 kill 之后不会自己拉起来**，你会把整套网络搞挂。

**正确做法**：给它发 **`SIGHUP`**（让它重读配置），而不是杀掉。

### ③ 开发板上「文件在」和「文件生效」是两回事

- 有的存储**重启后改动全丢**（换 inode / 没落盘）
- 文件权限**会在推送过程中丢掉**，尤其是**可执行位**
  ⇒ ★ **换可执行文件之后必须补 `chmod`**
- 换正在运行的脚本要用**原子替换**（先写临时文件再 `mv`），
  否则正在执行的进程可能读到**半个文件**

### ④ 判断"这个进程是不是我说的那个进程"

★ **不要用 `ps | grep` 或 `pgrep -f`**——它们会**匹配到自己**（你的 grep 命令本身就在进程表里）。

**正确做法**：读那个 pid 的 `/proc/<pid>/comm`，或者比 `/proc/<pid>/cmdline`。

> 这个坑我踩过：`pkill -f` **把自己也杀了**。
