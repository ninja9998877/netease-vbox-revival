## 一、进程间通信总线

| 项 | 值 |
|---|---|
| 总线类型 | **会话总线**（不是系统总线） |
| socket 路径 | `/tmp/dbus-XXXXXXXXXX` ★ **后缀每次开机随机** |
| 判据 | ★ 必须 `test -S`（**是 socket**），不能只判"文件存在" |
| 谁创建的 | 开机时拉起的总线守护进程 |

★ **坑**：我们自己的进程环境里**可能没有总线地址这个变量**。
`dbus-send` 不知道去哪条总线时，命令会在**写进 socket 之前就被丢掉**，
**一句报错都没有** ⇒ 表现是"发出去了、没反应"。

## 二、服务与接口

| 服务名 | 对象路径 | 角色 |
|---|---|---|
| `netease.ihw.player` | `/netease/ihw/player` | **嗓子**：播放 / 停止 |
| `netease.ihw.controller` | `/netease/ihw/controller` | **总控**：状态机 / LED / 播放器管理 |
| `netease.ihw.bt` | — | 蓝牙 |

**公共接口名**：`netease.ihw.SmartAudio.API`

### 调用签名

```
SmartAudio.API(uint32 flag,
               uint32 msgDests,
               uint32 cmd,
               uint32 jsonLen,
               string json)
```

★ **五个参数一个都不能少、类型一个都不能错**——少一个**不报错，只是什么都不发生**。

| 参数 | 说明 |
|---|---|
| `flag` | 实测填 `0` |
| `msgDests` | ★ **`1 << 模块号`**。播放器模块号 = 4 ⇒ 填 **16** |
| `cmd` | 命令码，见下 |
| `jsonLen` | ★★ JSON 的**字节数**（不是字符数！见下面的坑） |
| `json` | 载荷 |

## 三、命令码

| 码（hex） | 码（dec） | 含义 |
|---|---|---|
| `0x601` | 1537 | **播放**（载荷带 URL） |
| `0x602` | 1538 | 掐断当前播放 |
| `0x603` | 1539 | **停止** |
| `0x700` | 1792 | 原厂提示音：停 |
| `0x701` | 1793 | 原厂提示音：播 |

### `0x601` 的 JSON 载荷

```json
{"playerId":1,
 "src":"http://<你的HTTP服务>/xxx.mp3",
 "srcUuid":"http://<你的HTTP服务>/xxx.mp3",
 "gain":0,
 "backGroundUrl":""}
```

★ 逐字段说明：

| 字段 | 说明 |
|---|---|
| `playerId` | ★ **必须等于总控当前的 `curPlayer`**，否则播放会被掐掉 |
| `src` / `srcUuid` | 同一个 URL，填两遍（实测这样最稳） |
| `gain` | ★ **填 0**。这是**设备自己发同类命令时用的值**，不是音量调节手段 |
| `backGroundUrl` | 空串 |

> ★ **`gain` 不是音量杠杆**。真正的音量杠杆是 `DAC volume`（见第六节）。
> **不要在播放路径上动音量**——用设备当前的音量。

### `0x603` 的 JSON 载荷

```json
{"playerId":1}
```

## 四、`dbus-send` 的两个反直觉参数

```bash
dbus-send --session --print-reply --reply-timeout=200 \
  --dest=netease.ihw.player \
  /netease/ihw/player \
  netease.ihw.SmartAudio.API \
  uint32:0 uint32:16 uint32:1537 uint32:$LEN string:"$JSON"
```

| 参数 | 为什么 |
|---|---|
| ★ **必须有 `--print-reply`** | 去掉它 ⇒ **消息不 flush 就断开**，一个字送不到，而返回值还是 0 |
| ★ **超时必须很小（200ms）** | 播放器**只收不回**，否则干等到超时 ⇒ 每次说话**白等 2.5 秒** |

实测对照：

| 参数 | 结果 |
|---|---|
| 无 `--print-reply` | ✗ **没送到** |
| `--reply-timeout=2500` | ✓ 送到，但等 2.546 秒 |
| `--reply-timeout=200` | ✓ 送到，**0.239 秒** |
| `--reply-timeout=50` | ✓ 送到，0.087 秒 |

> ★ 这 200ms 只是 `dbus-send` **自己退出前**的等待，命令早就送到了。
> 所以**对"打断"来说真实延迟是 0**。

### ★★ `jsonLen` 的坑

必须是**字节数**。

```sh
# ✗ 错：busybox 的长度展开按【字符】算，JSON 里有中文就错
LEN=${#JSON}

# ✅ 对：
LEN=$(printf '%s' "$JSON" | wc -c)
```

★ 这个坑**只在载荷含中文时发作**——平时测都好好的。

## 五、总线命令（buscmd）

★ **和"命令码"是两层，别混**：命令码给播放器，**buscmd 给总控**（管状态与灯）。

| buscmd | 含义 |
|---|---|
| `2564` | 进"倾听中"状态（灯环白灯常亮） |
| `2560` / `2561` | 灯效控制 |
| `2569` | 对照/无副作用（★ 试新码前**先发它当阴性对照**） |

**调用形式**：发往 `netease.ihw.controller`，`msgDests = 1 << 3 = 8`。

★ **有些通道的载荷会顺带触发播放/出声**——试之前想清楚。

## 六、ALSA 控件（card 0）

| 控件 | numid | 真相 |
|---|---|---|
| **`DAC volume`** | 19 | ★★ **唯一的真音量杠杆** |
| `DAC mixer gain` | 20 | ❌ 纸闸门（值是 0 也正常） |
| `digital volume` | 21 | ❌ 纸闸门（★ 曾被我误判成真凶） |
| `headphone volume` | — | ❌ 名字最像音量，**但不是真杠杆** |
| `HP_L Mux` | — | ★ 声道选择开关，**指错 = 全哑** |

### `DAC volume` 参数

```
min=0   max=255   step=0.75dB   dBscale-min=-119.25dB
⇒ 159 ≈ 0dB（满刻度）
⇒ 0   = -119.25dB = 全哑
```

| 动作 | 命令 |
|---|---|
| 读 | `amixer -c 0 cget name='DAC volume'` |
| 写 | `amixer -c 0 cset name='DAC volume' 150,150` |

### `HP_L Mux` 的两个位置

| 值 | 位置 | 结果 |
|---|---|---|
| `0` | **DAC 直连耳机输出** | ✅ 有声音 |
| 其它 | 接进空模拟混音器（输入全关） | ❌ **整机全哑** |

```bash
amixer -c 0 cset name='HP_L Mux' 'DACL HPL Switch'
```

### ★★ 解析 `amixer cget` 输出的铁律

输出是**四行**：

```
numid=19,iface=MIXER,name='DAC volume'
  ; type=INTEGER,access=rw------,values=2,min=0,max=255,step=1
  : values=150,150                                    ← ★ 值在这
  | dBscale-min=-119.25dB,step=0.75dB,mute=0          ← 这是量程，不是值
```

★★ **绝不能用 `tail -1`** ⇒ 会永远读到 dBscale ⇒ 永远判成"错的" ⇒ **每轮无脑写一次**。

**正确**：

```sh
# 匹配特征串，不要用位置假设
dac_now() {
  amixer -c 0 cget name='DAC volume' 2>/dev/null | sed -n 's/^ *: values=//p'
}
```

★ `HP_L Mux` 那边则要取**最后一行**（它的值是 `values=0`）——
**两个控件的解析方式不同，因为输出格式不同**。别互相抄。

## 七、麦克风截流协议（自研）

### 传输

UDP，默认端口 **9998**。包上限 **1400 字节**（不超 MTU 惹分片），
其中包头 32 字节 ⇒ **载荷最多 1368 字节**。

### 包头（32 字节，小端）

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0 | `magic` | `0x5041544D`（内存里是 `"MTAP"`） |
| 4 | `ver` | 版本，当前 **2** |
| 8 | `seq` | 递增序号，接收端用来认丢包 |
| 12 | `frames` | 本包帧数 |
| 16 | `rate` | 采样率 |
| 20 | `ch` | 声道数 |
| 24 | `fmt` | ALSA 格式号（`2` = `S16_LE`） |
| 28 | `flags` | 见下 |

### `flags` 位域

| 位 | 含义 |
|---|---|
| `bit0` | `MT_F_DECIM`：这份流是**滤过 + 抽过**的 |
| `bit8` 起（高 24 位） | ★ **原始**采样率 |

★ **注意**：源码里那个结构体的注释写着"保留，现在恒 0"——
**那是注释过期了**。实际行为以上表为准（版本 2 起就在用 `flags`）。

> ★ 这也是个通用教训：**注释会和代码脱节。以代码为准，注释只当线索。**

### 环境变量（设备侧）

| 变量 | 默认 | 说明 |
|---|---|---|
| `MICTAP_HOST` | （你的接收端地址） | 目标地址 |
| `MICTAP_PORT` | `9998` | 目标端口 |
| `MICTAP_RATE` | `16000` | 探测失败时的兜底采样率 |
| `MICTAP_CH` | `2` | 兜底声道数 |
| `MICTAP_FMT` | `2` | 兜底格式（`S16_LE`） |
| `MICTAP_FILTER` | `1` | ★ **置 0 关掉滤波链**，退回原始码流（**安全阀**） |
| `MICTAP_DEBUG` | `0` | 置 1 打开 `/tmp/mictap.log` |
| `MICTAP_RAWDUMP` | — | 指了路径就原始字节转储（排障用） |
| `MICTAP_INJECT` | `/tmp/mictap_inject.pcm` | ★ **测试钩子**：把一个 PCM 文件当麦克风数据注入 |

★ **急停开关**：设备上存在 `/tmp/spk/mictap.off` ⇒ **整个不发**，**不用重启服务**。

### 关于 `MICTAP_INJECT`

★ 这是个**很值钱的调试钩子**：可以**不出声、不用真人说话**就跑完整条链。

> 我把它做进来的理由很实际：**屋里有人时不能随便让设备出声**，
> 而"对着音箱说话"这种测试**必然出声**。
> 有了注入，我可以在**完全静音**的情况下验证整条下游链路。

## 八、音频格式速查

| 项 | 值 |
|---|---|
| 麦克风真机格式 | **96000 Hz × 2 声道 × S24_LE** |
| 截流后送给识别 | **16000 Hz × 2 声道 × S16_LE** |
| 抽取倍数 | **6** |
| 上行速率 | 768 KB/s → **64 KB/s**（≈ 1/12） |

★ **滤波链顺序**（顺序不能换）：

```
S24 输入 → FIR 低通（抗混叠）→ 6 倍抽取 → 4 阶巴特沃斯高通 → int16
```

★ **为什么顺序不能换**：先抽取再低通 = **混叠已经发生了**，滤不回来。

## 十、自研进程间约定

### "我说过什么"登记簿

★ 所有**会出声**的路径都要往里登记。**查不到就放行**（fail-open）。

**为什么要 fail-open**：宁可偶尔漏判一次回声，
**也不能因为它挂了就把用户的话全吃掉**。

### 单实例锁（所有守护脚本通用）

```sh
# ★ 必须崩溃安全：mkdir 保原子性，锁里放 pid，
#   用 /proc/<pid>/cmdline 核实那个 pid 真的是本脚本 ⇒ 陈旧锁自动抢过来
```

★ **反面教材**：`mkdir "$LOCK" || exit 0` 且**从不删锁** ⇒
一次 `kill -9` 就**永久瘫痪**，而且**一声不响**。

### 出口格式约定

★ **每条路径的最后一行固定是 `XXX-OK` / `XXX-FAIL` / `XXX-TIMEOUT` / `XXX-SKIP`**。

**理由**：走通道时**空回复会被当成"没回话"**，接收端会**白等到超时**。
所以**一条出口都不留空**。

## 十一、判据速查（最值钱的一节）

| 我想知道 | ✅ 用什么判 | ❌ 不要用 |
|---|---|---|
| 注入库生效了吗 | `grep <库名> /proc/<pid>/maps` | "文件在不在" |
| 播放命令送到了吗 | ★ **设备来取文件了吗**（HTTP 访问日志） | `dbus-send` 的返回值 |
| 命令真的执行了吗 | 设备侧日志里的**命令 ID** | "我发出去了" |
| 设备在线吗 | **连接跟踪表** | `ping`（可能有黑洞/防火墙） |
| 网络通吗 | ★ **查 TCP 端口** | ★ **`ping`（黑洞下 ICMP 可能仍通）** |
| 那个进程是我说的那个吗 | `/proc/<pid>/comm` | `ps \| grep`（会自匹配） |
| 守护还活着吗 | ★ **日志有没有新行** | "进程看起来在跑" |
| 配置生效了吗 | ★ **重启一次再看** | "我改了" |
| 这个控件是真杠杆吗 | ★ **逐档实测，一次只动一个** | 控件的名字 |
| 慢的是哪一环 | ★ **量** | "我觉得是模型慢" |
